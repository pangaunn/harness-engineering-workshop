What is harness engineering?

  • A harness is everything in the repo around the model: instructions, docs, tests, checks, CI, error messages.
  • You can't change the model. You can change the harness.
  • Today: a harness for maintenance. An agent can only follow a rule it can check. When the repo verifies its own rules, the agent can work alone and fix its own mistakes.
  • Five subsystems of a harness (from Learn Harness Engineering), today's three highlighted:
    instructionsstateverificationscopesession lifecycle

Markdown explains a rule. Code enforces it. The error message re-teaches it.

Why a harness?

  • Models keep getting better. They still say "done" when they aren't.
  • A better model writes more code, faster, so there's more for you to check.
  • Reading every line doesn't scale. The repo has to check the work, not you.

Stop trusting. Start verifying.

The app

  • Hotel booking API in Go, standard library, SQLite, no Docker.
  • handler → service → repository, plus model and jobs.
  • 5 endpoints: rooms, quotes, bookings, cancel, revenue report.
  • You don't need to know Go well. The agent writes the code; you build the harness.

The big picture

  • Arrows are imports, as the code is today (r1-without).
  • model holds plain structs that every package uses (left out of the picture). cmd/server wires everything together and starts the nightly job.
  • One app, four rounds: you'll maintain this same code all session.

How the rounds run

R1  r1-without | r1-with                (split: half the room each)
        │ our R1 result
R2  r2-without ─► r2-mine ─► compare with r2-with      your harness starts from r2-kit
        │ our R2 result
R3  r3-without ─► r3-mine ─► compare with r3-with      + your r2-mine harness
        │ our R3 result
R4  r4-without ─► r4-mine ─► compare with r4-with      + your r3-mine harness
  • The code resets each round; your harness carries over. Every round starts from our result of the previous round, so everyone has the same code.
  • Rounds 2–3, four steps: 1. run on without · 2. build your harness · 3. rerun the same prompt · 4. compare with ours. Round 4 works like real life: think about what the harness needs for the next prompt, let the agent update it, then send the prompt.
  • Commit your harness at the end of every round (r2-mine, r3-mine, …). It's what you bring to the next one.
  • Keep WORKSHOP.md open in a browser (GitHub, main branch). The round branches don't contain it.

Rules for every run

  1. Clean tree: git status shows nothing to commit.
  2. Fresh agent session, in the repo root.
  3. Paste the prompt exactly. Add nothing.
  4. Agent asks a question → reply only Use your best judgment.
  5. Agent says done → stop. Don't ask for fixes.
  6. Same agent tool for the whole round.

Round 2 · What's new since Round 1

  • r2-without = r1-without + our R1 migration (money is Money) + our R1 harness:
AGENTS.md (CLAUDE.md: @AGENTS.md)
# AGENTS.md
Hotel booking API in Go: standard library `net/http`, SQLite via `modernc.org/sqlite` (no cgo).
Layered as handler → service → repository. Amounts are Thai baht and include 7% VAT.
## Layout
```
cmd/server/              entry point and wiring
internal/handler/        HTTP, JSON in/out
internal/service/        booking, room, availability, pricing, payment, report
internal/repository/     SQLite access, one file per table
internal/model/          plain structs shared by every layer
internal/jobs/           background jobs (nightly revenue report)
```
## Commands
- `make check` runs gofmt, `go vet` and every test, including the integration tests
  (`-tags integration`) that plain `go test ./...` skips. CI runs the same command.
- `go run ./cmd/server` starts the API on `:8080`.
## Verification
You are not done until `make check` passes. Paste its final output in your final message.
Never say tests pass unless you ran them in this session.
Makefile
check: fmt vet test

fmt:
	@out=$$(gofmt -l .); if [ -n "$$out" ]; then echo "gofmt: these files need formatting (run gofmt -w .):"; echo "$$out"; exit 1; fi
vet:
	go vet -tags integration ./...
test:
	go test -tags integration ./...
CI .github/workflows/check.yml runs make check on every push
  • From here on, every agent runs everything before it says done.
  • Nothing says where code goes. That's this round.

Round 2 · Why rules about where code goes?

  • Agents copy the code they see. One shortcut becomes the pattern for the next ten changes.
  • A wrong import breaks no test: make check stays green.
  • Nobody spots one import line in a 300-line diff.
  • The bill comes later: tests suddenly need a database, import cycles, one change breaks three packages.
  • If the rule lives only in a senior dev's head, the agent can't follow it.

Example (a blog, not this app): should post import user, or should a third package use both?

Round 2 prompt (step 1)

git checkout r2-without
When at least 2/3 of a room type's rooms are already booked for a night, that night's rate is 20% higher. pricing.Quote should get occupancy from the availability service itself, so callers don't have to pass it in.
  • Write down your "before" result. Then git diff: where did the new logic go, and what does each changed package import now?

Step 2 · Get the kit

git reset --hard && git clean -fd
git switch -c r2-mine
git checkout origin/r2-kit -- .
  • internal/archtest/arch_test.go: reads real imports with go/parser. You don't need to edit it (unless you're done early: the error messages live there).
  • internal/archtest/rules.go: empty rules. You fill these in.
  • Makefile: make check
  • AGENTS.md: headings only (CLAUDE.md points to it)

Step 2 · Build the rules

  1. go test ./internal/archtest/ → every package "not registered".
  2. Fill in layers: put every package under internal/ into a layer.
  3. Fill in allowed: which layer may import which. Run the test until it passes.
  4. Test your rule: add an import of service/pricing into service/payment. Does it fail? Remove it again.
  5. AGENTS.md: one sentence per rule + "You are not done until make check passes."
  6. git add -A && git commit -m "our harness"
  • make check still fails on this branch: that's the bug the agent will fix.
  • Done early? Make your error message say where the logic should go instead · Try to put the logic in the wrong place in a way your rules still accept.

Step 3 · Rerun

  • Fresh session, same tool, same prompt.
  • Write down your "after" result.
  • git reset --hard && git clean -fd (your harness commit stays).

Step 4 · Compare with ours

git diff r2-mine origin/r2-with -- AGENTS.md CLAUDE.md Makefile internal/archtest docs
  • Where do your rules differ from ours?
  • Would ours have stopped something yours let through?

Reveal: Round 2

  • Our allowed map: the domain layer may import repository and model, not other domains.

  • The error message the agent sees:

    FAIL: internal/service/payment imports internal/service/pricing
  Domain services must not import each other.
  If logic needs two domains, move it into an aggregate (e.g. service/booking).
  See docs/architecture.md#rules
  • A sentence in a doc vs the same rule as a failing test: which one held?
  • Your kit said only what broke. Ours also says where the logic should go. The error message is the one piece of the harness the agent is guaranteed to read.

Round 3 · Why a workflow for bug fixes?

  • The bug shipped because no test covered it. "All green" after the fix proves nothing: it was all green before the fix, too.
  • A test written after the fix confirms the code, not the bug. Only a test that failed first shows the fix did something.
  • No test that fails on the bug → the next change can bring it back, and nothing notices.
  • "While I'm here" cleanups mixed into a fix: when something breaks, which part did it?
  • Red → green → refactor leaves no trace in the final diff. You can't tell from the code whether red ever happened.

Example (a blog, not this app): "comment counts are off by one". What's the first thing you write?

Step 3 · Rerun, Step 4 · Compare

  • Fresh session, same tool, same prompt. Write down "after".
git diff r3-mine origin/r3-with -- AGENTS.md CLAUDE.md Makefile scripts
  • Which parts of your workflow are sentences an agent may ignore? Which are commands that fail?

Reveal: Round 3

  • Our workflow in AGENTS.md:

    1. Red: write a test that shows the bug (or the new behaviour) and see it fail on the current code.
2. Green: make the smallest change that makes it pass.
3. Refactor: tidy only the code you changed in step 2. Tests stay green.
4. Done: `make check` passes. List anything else you noticed under "Follow-ups" in your
   final message instead of changing it.

  • Our make check runs your changed tests against the old code and needs one to fail:

    red-first: FAIL: Go code changed but no test did.
red-first: FAIL: your changed tests also pass on the code at HEAD.
  They don't reproduce the bug, so they don't prove the fix.
red-first: ok, your changed tests fail on the code at HEAD:
  --- FAIL: TestQuote_CheckOutNightIsNotBusy
      booking_test.go:148: total 1861.80, want 1551.50 (1 of 3 rooms booked)
  • "A test changed" is easy to fake. "A test failed first" isn't.
  • Checkable → in the command. Judgment (what "refactor" may touch) → in Markdown.

Round 4 · Before you send the next prompt

You maintain this app, and this is the next task. Is your harness ready for it?

Add POST /group-bookings: book 2–5 rooms of one room type for the same dates under one guest name. All rooms are booked or none are. Group stays follow the same stay rules as single bookings. Every room in a group pays the same price: the busy-night surcharge uses occupancy before the group, not the group's own rooms. Group bookings live in their own package, service/groupbooking, so booking doesn't keep growing. Request: the /bookings fields plus "rooms". Response: 201 with {"bookings": [...], "total": ...}.

What would you add so the agent keeps delivering quality software, now and after this task?

Step 1 · Think, then let your agent update the harness

git checkout r4-without && git switch -c r4-mine
git checkout r3-mine -- AGENTS.md CLAUDE.md Makefile scripts internal/archtest

(No working round 3 harness? Skip the second line: r4-without already has ours.)

  1. As a pair, list what's missing (4 min). Write it down before you open the agent.
  2. New session. Give the agent your list, not the prompt. Let it update the harness: AGENTS.md, checks in make check. Review what it did.
  3. Prove every new check: make the mistake on purpose → make check red. Undo.
  4. git add -A && git commit -m "our harness"

Step 2 · Send the prompt

  • Fresh session, same tool. Paste the prompt from slide 31. Rules for every run apply.
  • When it says done:
git status --short && git diff internal/archtest/rules.go && make check
  • Which packages are new, and which layer did each get? Did allowed change? Did your harness stop anything, or did the agent change it?

Step 3 · Compare with ours

git diff HEAD origin/r4-with -- AGENTS.md Makefile scripts internal/archtest
  • What does ours check that yours doesn't? And the other way round?
  • Which of your rules can the agent change as easily as the code?

Reveal: Round 4

  • Our answer: the shared stay rules become a new domain, stay; groupbooking is a new aggregate. layers grows by two; allowed is unchanged.

  • Our make check lets the rules grow and stops them shrinking:

    harness-guard: FAIL: `allowed` in internal/archtest/rules.go changed.
  Only a human may loosen the rules. Registering a package in `layers` is fine.
  Fix the design instead (see "Adding a package" in AGENTS.md), or stop and ask.

FAIL: AGENTS.md does not name `groupbooking` (aggregate), `stay` (domain)

The rules may grow. Only a human may loosen them.

Audit your own repo

  1. Verification: one command an agent must run before "done"? Does CI run the same one?
  2. Architecture: which rules live only in people's heads? Which could be a test?
  3. Scope: does your repo say what "done" means? Which parts could be a command?
  4. Extension: does the repo say how to add a module, and stop anyone loosening the rules?

Takeaways

  • Markdown explains. Code enforces. The error message re-teaches.
  • Put everything checkable into one command, and make CI run the same one.
  • Harnesses rot too: entropy control, scheduled cleanup agents.
  • Take your harness branch home.
